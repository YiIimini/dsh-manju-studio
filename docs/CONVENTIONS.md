# 工程约定（本仓库与其产出的新项目都遵守）

> 用户 2026-09-23 明确要求：**新建项目必须具备功能模块化、解耦性等优势，以保证后续升级维护。**
> 这份文件把那句话变成可执行、可检查的标准——写代码按它对，做评审也按它查。

## 一、模块划分：一个模块一个职责

按**能力**切分，不按"顺手放一起"：

| 层 | 职责 | 不该做的事 |
|---|---|---|
| 入口 / CLI | 解析参数、调度子命令 | 不写业务逻辑（入口应当很薄） |
| 领域逻辑 | 分镜、提示词、字幕、质检规则 | 不直接碰进程、网络、磁盘细节 |
| 基础设施 | ComfyUI 客户端、ffmpeg 封装、文件与路径 | 不含领域判断（"这镜合不合格"不在这里） |
| 表现 / UI | 渲染与交互 | 不直接读写磁盘（走宿主接口） |

判据：**如果你能用一句话说清这个模块负责什么，且这句话里不出现"和"，它就是合格的。**

## 二、解耦：三条硬边界

1. **只走公开接口**：模块之间只通过导出的函数/命令调用；
   **禁止**伸手读对方内部状态，**禁止**代写对方负责的文件
   （例如媒体模块不许自己去改项目的 shots.json）。
2. **依赖单向、无环**：基础设施 → 领域 → 入口，不许反向 import。
   出现环就说明职责切错了，不是"加个 lazy import"能了事的。
3. **配置与逻辑分离**：默认值与常量集中一处；可变参数走 json/env；
   不许把路径、模型名、阈值散落在各处硬编码。

## 三、可维护性的具体验收项

新建项目/新增模块时逐条过：

- [ ] 模块目录清晰（不是把所有东西堆在一个文件里），README 写明每个模块的职责
- [ ] 入口文件只做参数解析 + 调度
- [ ] 每个模块**可单独测**，且测试与模块同名同目录便于定位
- [ ] **一条命令跑完全部检查**（本仓库是 `tools/gate.cmd`），且它有退出码
- [ ] 关键不变量写成断言（例如"新状态必须追加在状态列表末尾""这个组件必须定义在模块级"），
      而不是写在注释里靠人记
- [ ] 变更可回滚：仓库在 git 里，重产物不入库但有备份目录约定

## 四、本仓库的已知债与拆解方向

`tools/manju-headless.py` 目前是**单文件约 2100 行**（历史累积：构建、同步、渲染、质检、
合成、封面、分集、语音验收、系列资产池全在一个文件里）。它已经踩到单文件的两条红线：
改一处要通读全局、模块边界只能靠人记。

**拆解方向**（维护窗口执行，不打断正在跑的渲染）：

```
tools/manju/            # 包
  paths.py     项目路径与项目解析
  prompts.py   H3 六段式组装、空间锚点、普通话锁
  comfy.py     ComfyUI 客户端、显存归还、图提交
  media.py     ffmpeg 封装、字幕、合成
  covers.py    封面生成
  episodes.py  分集与系列资产池
  qc.py        质检与自检报告
  asr.py       语音验收
  cli.py       argparse + 调度（薄入口）
tools/manju-headless.py  # 只保留 `from manju.cli import main`
```

拆解时**先用断言锁住现有行为**（现有 11 个套件就是安全网），再一段一段搬，
每搬一块跑一次 `gate.cmd`——保证任何一步都能停、都能回滚。
